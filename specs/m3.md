# M3 — Tailored applications, verified contacts and unsent Gmail drafts

## Scope and truth boundary

M3 turns an M2D vacancy into a durable, reviewable application packet. It uses the versioned candidate profile, exact vacancy record and approved local document manifest. Generation is deterministic (`grounded-template-v1`), makes no network or model call, and labels AI project evidence without inferring employer, client or production AI tenure.

M3 never sends mail or submits an application. The Gmail adapter exposes draft creation only. Google `gmail.compose` consent can technically permit sending, so the application boundary, rather than OAuth alone, enforces no-send behavior. Attachments and profile-card insertion remain manual.

## Durable model

Schema v9 adds one current packet per stable JobKey, immutable packet versions, actual employer questions with source references, versioned answers, contact evidence and an idempotent Gmail draft-operation journal. A content hash prevents regeneration when the profile, vacancy, documents and missing facts are unchanged. User edits append a version; they never overwrite a saved Gmail draft.

Packet statuses are `TEXT_PREPARED`, `NEEDS_USER_INFORMATION`, `CONTACT_VERIFICATION_PENDING`, `REVIEW_DRAFT_READY`, `GMAIL_DRAFT_PENDING`, `GMAIL_DRAFT_SAVED`, `GMAIL_DRAFT_UNCERTAIN` and `BLOCKED_INCOMPATIBLE`. Prepared text and saved drafts remain distinct from manual `SUBMITTED` tracking.

## Eligibility and contacts

Known closure or hard incompatibility blocks drafting. Unknown headcount, payroll or India eligibility stays visible in the packet and dashboard but does not block portal text preparation. A Gmail draft requires a verified role-related contact with an email and public source URL or received-message reference. No-reply and unverified contacts cannot be used. No email pattern is guessed.

## Questions and documents

Questions are stored only from an identified employer portal/message or explicit user input. Notice and expected-compensation proposals may use the corresponding confirmed profile facts; work authorization, current compensation, joining date and other unsupported fields remain `NEEDS_USER_INFORMATION`. Character limits are enforced.

New-application HTML includes the required red profile-card marker and manual file instructions. The answer bank is never an attachment. A cover letter is not requested by default. Local exports contain the application queue, text, actual questions/answers, contact evidence, missing information and audit data and remain `NOT_UPLOADED`.

## External blockers

Live Gmail needs a user-owned Desktop OAuth client, optional Gmail dependencies and explicit combined readonly/compose consent. Missing canonical documents are reported from the ignored local manifest. Synthetic adapter verification is not live Gmail verification.

## Historical standing unsent-draft instruction (superseded by R2)

The user's instruction to create drafts when a verified role-related recruiter is found supersedes the earlier concrete-batch approval requirement for NEW_APPLICATION unsent drafts only. Persist that trusted local instruction outside Git. The coordinator checks current eligibility/history/contact evidence, binds an exact single-use snapshot grant, and journals before dispatch. Backend and adapter checks remain. Never send, guess addresses, overwrite an existing draft, or retry uncertain outcomes. No automatic recruiter replies or attachments. Research/preparation actions trigger eligible drafting; GETs remain read-only. Missing connection, ineligible jobs and missing documents are reported as distinct blockers, never ?awaiting batch approval.?

Opportunities defaults to highest fit descending. Minimum fit is a threshold. Empty filter results explain restrictive date/experience filters; navigation messages must clear when leaving their section.
